# CIMD

## How trust is established between the client and the IDP

- Domain Ownership as Identity:
Instead of using a random string generated by the Identity Provider (IdP), the Client uses its own public HTTPS URL as the client_id (e.g., https://example.com). Because the client controls the DNS and hosting for example.com, it claims ownership of that identity.

- Real-Time Fetching and TLS:
When the client initiates a request, the IdP extracts the client_id URL and performs a real-time HTTP GET request to fetch the metadata document. Trust at this layer relies on standard Web PKI (HTTPS). The IdP verifies the TLS certificate of ://example.com, ensuring it is communicating with the actual owner of the domain and not an impersonator.

- The "Self-Referential" Matching Rule:
To prevent an attacker from hosting a malicious app on a shared domain or redirecting the IdP to a different file, the IdP strictly enforces a matching rule:

  - Inside the fetched JSON document, there is a client_id field.
  - The IdP verifies that the exact URL it used to fetch the document matches the client_id string declared inside the document. If they do not match perfectly, the IdP rejects the client.

- Cryptographic Proof (Proof of Possession) :
To prove that the client software making the request is actually authorized by the domain owner (and not someone just copying the public client_id URL), the metadata document publishes the client's public keys using a JSON Web Key Set (jwks or jwks_uri).

  - The Document: Houses the client's Public Key.
  - The Request: The client signs its authentication request (or a software statement) using its private key.
  - The Verification: The IdP uses the public key it just fetched from the trusted domain to verify the signature. If the signature is valid, it proves the client possesses the matching private key.
